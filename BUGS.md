## Подробное описание дефектов

### BUG-01: Любой авторизованный пользователь может удалить чужое объявление (IDOR)

- **Серьёзность:** Critical (S1)
- **Ручка:** `DELETE /api/2/item/{id}`
- **Предусловия:**
  1. Зарегистрированы и авторизованы два разных пользователя: Пользователь 1 (`sellerID_1`, `token_1`) и Пользователь 2 (`sellerID_2`, `token_2`).
  2. Пользователь 1 создал объявление (`POST /api/1/item`), получен его UUID `<item_id>`.
- **Шаги воспроизведения:**
  1. От имени **Пользователя 2** (`Authorization: Bearer <token_2>`) отправить запрос на удаление объявления Пользователя 1:
     ```bash
     curl -i -X DELETE "https://qa-internship.avito.com/api/2/item/<item_id>" \
       -H "Authorization: Bearer <token_2>"
     ```
  2. От имени Пользователя 1 запросить своё объявление:
     ```bash
     curl -i "https://qa-internship.avito.com/api/1/item/<item_id>" \
       -H "Authorization: Bearer <token_1>"
     ```
- **Фактический результат:**
  - На шаге 1 сервер возвращает `HTTP/1.1 200 OK`.
  - На шаге 2 объявление Пользователя 1 удалено (`HTTP/1.1 404 Not Found`).
- **Ожидаемый результат:**
  - На шаге 1 сервер отклоняет удаление чужого объявления с кодом `403 Forbidden` (или `404 Not Found`).
  - На шаге 2 объявление Пользователя 1 остаётся в системе (`HTTP/1.1 200 OK`).

### BUG-02: Создание объявления с отрицательной ценой (`price < 0`) проходит успешно

- **Серьёзность:** Major (S2)
- **Ручка:** `POST /api/1/item`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<seller_id>`, `<token>`).
- **Шаги воспроизведения:**
  1. Отправить запрос на создание объявления с `price: -1`:
     ```bash
     curl -i -X POST "https://qa-internship.avito.com/api/1/item" \
       -H "Authorization: Bearer <token>" \
       -H "Content-Type: application/json" \
       -d '{"sellerID": <seller_id>, "name": "test-neg-price", "price": -1, "statistics": {"likes": 1, "viewCount": 1, "contacts": 1}}'
     ```
- **Фактический результат:** `HTTP/1.1 200 OK`, объявление сохраняется в базе с отрицательной ценой (`{"status": "Сохранили объявление - <uuid>"}`).
- **Ожидаемый результат:** `HTTP/1.1 400 Bad Request`, объявление с отрицательной ценой не создаётся.

- **Серьёзность:** Major (S2)
- **Ручка:** `POST /api/1/item`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<seller_id>`, `<token>`).

### BUG-04: Невозможно создать объявление с нулевыми показателями статистики или нулевой ценой (`0` считается пустым полем)

- **Серьёзность:** Major (S2)
- **Ручка:** `POST /api/1/item`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<seller_id>`, `<token>`).
- **Шаги воспроизведения:**
  1. Отправить запрос на создание нового объявления с нулевой статистикой (`likes: 0, viewCount: 0, contacts: 0`) либо с бесплатной ценой (`price: 0`):
     ```bash
     curl -i -X POST "https://qa-internship.avito.com/api/1/item" \
       -H "Authorization: Bearer <token>" \
       -H "Content-Type: application/json" \
       -d '{"sellerID": <seller_id>, "name": "new-item-zero-stats", "price": 1000, "statistics": {"likes": 0, "viewCount": 0, "contacts": 0}}'
     ```
- **Фактический результат:**
  - `HTTP/1.1 400 Bad Request`
  - Тело ответа: `{"result":{"message":"поле likes обязательно","messages":{}},"status":"400"}` (аналогично `400` возвращается при `viewCount: 0`, `contacts: 0` и `price: 0` — валидатор на бэкенде проверяет `value != 0` вместо проверки наличия поля в JSON).
- **Ожидаемый результат:** `HTTP/1.1 200 OK`, объявление успешно создаётся со значениями статистики `0` (для нового объявления 0 лайков, просмотров и контактов — естественное начальное состояние) и с ценой `0` («отдам даром»).

### BUG-05: Ручки статистики v1 и v2 возвращают данные после удаления объявления

- **Серьёзность:** Major (S2)
- **Ручки:** `GET /api/1/statistic/{id}`, `GET /api/2/statistic/{id}`
- **Предусловия:**
  1. Пользователь создал объявление, получен `<item_id>`.
  2. Объявление удалено запросом `DELETE /api/2/item/<item_id>` (`HTTP 200`), `GET /api/1/item/<item_id>` возвращает `404`.
- **Шаги воспроизведения:**
  1. Запросить статистику удалённого объявления по v1 и v2:
     ```bash
     curl -i "https://qa-internship.avito.com/api/1/statistic/<item_id>" -H "Authorization: Bearer <token>"
     curl -i "https://qa-internship.avito.com/api/2/statistic/<item_id>" -H "Authorization: Bearer <token>"
     ```
- **Фактический результат:** Обе ручки возвращают `HTTP/1.1 200 OK` и массив со статистикой `[{"contacts":43,"likes":21,"viewCount":11}]`.
- **Ожидаемый результат:** `HTTP/1.1 404 Not Found`, так как объявление удалено.

### BUG-06: Несоответствие HTTP-статуса (404) и поля `status` в теле ответа ("400") при невалидном UUID в `GET /api/2/statistic/{id}`

- **Серьёзность:** Minor (S3)
- **Ручка:** `GET /api/2/statistic/{id}`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<token>`).
- **Шаги воспроизведения:**
  1. Запросить статистику v2 с невалидным идентификатором (`not-a-uuid`):
     ```bash
     curl -i "https://qa-internship.avito.com/api/2/statistic/not-a-uuid" \
       -H "Authorization: Bearer <token>"
     ```
- **Фактический результат:**
  - HTTP-статус ответа: `HTTP/1.1 404 Not Found`
  - Тело ответа: `{"result":{"message":"передан некорректный идентификатор объявления","messages":null},"status":"400"}`
  - Аналогично воспроизводится для `id = %20`. При этом в версии v1 (`GET /api/1/statistic/not-a-uuid` или `%20`) корректно возвращается `HTTP/1.1 400 Bad Request` и `"messages": {}` (в v2 — `null`).
- **Ожидаемый результат:** HTTP-статус ответа `400 Bad Request` в соответствии с форматом ошибки и поведением v1.

### BUG-09: Неинформативное сообщение об ошибке и сломанный формат ответа при ошибке типов / переполнении полей

- **Серьёзность:** Trivial (S4)
- **Ручка:** `POST /api/1/item`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<seller_id>`, `<token>`).
- **Шаги воспроизведения:**
  1. Отправить запрос на создание объявления с числом `price`, превышающим `int64` (либо с дробным значением `likes: 1.5`):
     ```bash
     curl -i -X POST "https://qa-internship.avito.com/api/1/item" \
       -H "Authorization: Bearer <token>" \
       -H "Content-Type: application/json" \
       -d '{"sellerID": <seller_id>, "name": "Космическая цена", "price": 99999999999999999999999999999, "statistics": {"likes": 1, "viewCount": 1, "contacts": 1}}'
     ```
- **Фактический результат:** `HTTP/1.1 400 Bad Request`, но тело ответа:
  ```json
  {"result": {"message": "", "messages": {}}, "status": "не передано тело объявления"}
  ```
  Текст ошибки вводит в заблуждение (тело было передано, произошла ошибка декодирования/типа поля), причём `result.message` пустое, а текст попал в поле `status`.
- **Ожидаемый результат:** `HTTP/1.1 400 Bad Request` с корректным описанием ошибки валидации поля в `result.message` и `"status": "400"`.

### BUG-10: Состояние гонки (Race Condition) при конкурентном удалении объявления

- **Серьёзность:** Major (S2)
- **Ручка:** `DELETE /api/2/item/{id}`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<token>`), создано объявление с UUID `<item_id>`.
- **Шаги воспроизведения:**
  1. Отправить 5 параллельных запросов `DELETE /api/2/item/<item_id>` (например, через `ThreadPoolExecutor(max_workers=5)` в Python):
     ```python
     with ThreadPoolExecutor(max_workers=5) as pool:
         codes = list(pool.map(lambda _: requests.delete(
             f"https://qa-internship.avito.com/api/2/item/{item_id}",
             headers={"Authorization": f"Bearer {token}"},
         ).status_code, range(5)))
     ```
- **Фактический результат:** Получено `{200: 2, 404: 3}` — сразу два конкурентных запроса вернули `HTTP 200 OK` на удаление одного и того же объявления (вероятно, проверка существования записи и удаление не атомарны, без проверки `rows_affected == 1`). При этом конкурентная регистрация `POST /api/1/register` с одинаковым `username` работает корректно (`{201: 1, 409: 4}`).
- **Ожидаемый результат:** Ровно один запрос возвращает `200 OK`, а все остальные 4 — `404 Not Found` (`{200: 1, 404: 4}`).

### BUG-11: Несоответствие HTTP-статуса (404) и поля `status` ("500") в теле ответа при удалении несуществующего объявления

- **Серьёзность:** Minor (S3)
- **Ручка:** `DELETE /api/2/item/{id}`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<token>`).
- **Шаги воспроизведения:**
  1. Отправить запрос на удаление несуществующего валидного UUID (например, `00000000-0000-0000-0000-000000000000` или случайного UUID v4):
     ```bash
     curl -i -X DELETE "https://qa-internship.avito.com/api/2/item/00000000-0000-0000-0000-000000000000" \
       -H "Authorization: Bearer <token>"
     ```
- **Фактический результат:**
  - HTTP-статус ответа: `HTTP/1.1 404 Not Found`
  - Тело ответа: `{"result":{"message":"","messages":null},"status":"500"}`
  - В теле указан код `"500"` (внутренняя ошибка сервера) и пустое сообщение, тогда как соседняя ручка `GET /api/1/item/{id}` для того же UUID корректно возвращает `"status": "404"` и `"message": "item ... not found"`.
- **Ожидаемый результат:** В теле ответа `"status": "404"` и понятное сообщение об ошибке в `result.message`.

### BUG-12: Отсутствует ограничение максимальной длины поля `name` при создании объявления

- **Серьёзность:** Minor (S3)
- **Ручка:** `POST /api/1/item`
- **Предусловия:** Зарегистрирован и авторизован пользователь (`<seller_id>`, `<token>`).
- **Шаги воспроизведения:**
  1. Отправить `POST /api/1/item` с полем `name` длиной 5000 символов (`"Ж" * 5000`).
- **Фактический результат:** `HTTP/1.1 200 OK`, объявление с заголовком из 5000 символов успешно сохраняется.
- **Ожидаемый результат:** `HTTP/1.1 400 Bad Request` — должна действовать валидация разумной максимальной длины названия объявления.
